# OpenGL

여정을 시작하기 전에 먼저 OpenGL이 실제로 무엇인지 정의해야 합니다. OpenGL은 흔히 그래픽과 이미지를 조작하는 데 사용할 수 있는 거대한 함수 집합을 제공하는 API(Application Programming Interface)로 간주됩니다. 하지만 OpenGL 자체는 API가 아니며, [Khronos Group](https://www.khronos.org/)에서 개발하고 관리하는 **명세(Specification)**일 뿐입니다.

![OpenGL Logo](https://learnopengl.com/img/opengl.png)

OpenGL 명세는 각 함수의 결과/출력이 무엇이어야 하고 어떻게 동작해야 하는지 정확히 규정합니다. 그리고 이 함수가 어떻게 동작할지에 대한 솔루션을 구현하는 것은 해당 명세를 **구현(Implement)**하는 개발자의 몫입니다. OpenGL 명세는 구현에 대한 세부 사항을 제공하지 않기 때문에, 실제 개발된 OpenGL 버전들은 결과가 명세를 준수(하여 사용자에게 동일하게 보임)하는 한 서로 다른 구현을 가질 수 있습니다.

실제 OpenGL 라이브러리를 개발하는 사람들은 주로 그래픽 카드 제조업체입니다. 여러분이 구매하는 각 그래픽 카드는 해당 카드(시리즈)를 위해 특별히 개발된 특정 버전의 OpenGL을 지원합니다. Apple 시스템을 사용할 경우 OpenGL 라이브러리는 Apple이 직접 관리하며, Linux에서는 그래픽 공급업체의 버전과 애호가들의 자체 라이브러리가 혼합되어 존재합니다. 이는 OpenGL이 이상 동작을 보일 때 대부분 그래픽 카드 제조업체(또는 라이브러리 개발/유지관리자)의 잘못일 가능성이 높음을 의미합니다.

대부분의 구현이 그래픽 카드 제조업체에 의해 제작되기 때문에, 구현에 버그가 발생하면 일반적으로 비디오 카드 드라이버를 업데이트하여 해결합니다. 해당 드라이버에는 카드가 지원하는 최신 버전의 OpenGL이 포함되어 있습니다. 이것이 그래픽 드라이버를 주기적으로 업데이트하는 것이 항상 권장되는 이유 중 하나입니다.

Khronos는 모든 OpenGL 버전에 대한 명세 문서를 공공에 공개하고 있습니다. 관심 있는 독자는 본 튜토리얼에서 사용할 OpenGL 버전 3.3의 명세를 [여기](https://www.khronos.org/registry/OpenGL/specs/gl/glspec33.core.pdf)에서 확인할 수 있습니다. OpenGL의 세부 사항을 파악하기에 좋은 자료입니다(구현이 아닌 결과만을 주로 설명한다는 점에 주의하세요). 명세는 또한 함수들의 **정확한** 동작 원리를 찾는 데 훌륭한 참고 자료가 됩니다.

## 코어 프로필 vs 즉시 실행 모드 (Core-profile vs Immediate mode)

과거에 OpenGL을 사용한다는 것은 그래픽을 그리기 쉬운 방식인 **즉시 실행 모드(Immediate mode, 고정 기능 파이프라인이라고도 함)**로 개발함을 의미했습니다. OpenGL의 대부분의 기능은 라이브러리 내부에 숨겨져 있었고 개발자는 OpenGL이 계산을 수행하는 방식을 크게 제어할 수 없었습니다. 개발자들은 결국 더 많은 유연성을 원하게 되었고, 시간이 지남에 따라 명세는 결과적으로 더 유연해져 개발자가 그래픽을 더 많이 제어할 수 있게 되었습니다. 즉시 실행 모드는 사용하고 이해하기 매우 쉬웠지만, 극도로 비효율적이었습니다. 이러한 이유로 명세는 버전 3.2부터 즉시 실행 모드 기능을 폐기(Deprecated)하기 시작했고, 옛 폐기된 기능을 모두 제거한 OpenGL 명세의 한 부문인 **코어 프로필(Core-profile)** 모드로 개발하도록 권장하기 시작했습니다.

OpenGL의 코어 프로필을 사용할 때, OpenGL은 우리에게 현대적인 방식을 사용하도록 강제합니다. OpenGL의 폐기된 함수 중 하나를 사용하려고 하면 OpenGL은 에러를 발생시키고 렌더링을 중단합니다. 현대적 접근 방식을 배우는 것의 장점은 매우 유연하고 효율적이라는 점입니다. 하지만 학습하기가 더 어렵기도 합니다. 즉시 실행 모드는 OpenGL이 수행하는 *실제* 연산의 많은 부분을 추상화하여 배우기는 쉬웠지만 OpenGL이 실제로 어떻게 작동하는지 파악하기는 어려웠습니다. 반면 현대적 접근 방식은 개발자가 OpenGL과 그래픽스 프로그래밍을 진정으로 이해할 것을 요구하며, 다소 어렵긴 하지만 훨씬 더 많은 유연성, 더 높은 효율성, 그리고 무엇보다 그래픽스 프로그래밍에 대한 한층 깊은 이해를 제공합니다.

이 책이 코어 프로필 OpenGL 버전 3.3을 대상으로 하는 이유도 바로 여기에 있습니다. 비록 더 어렵지만 충분한 가치가 있습니다.

현재는 더 높은 버전의 OpenGL(작성 시점 기준 4.6)을 선택할 수 있는데, 그렇다면 "OpenGL 4.6이 나왔는데 왜 OpenGL 3.3을 배워야 하는가?"라는 의문이 들 수 있습니다. 이에 대한 답은 비교적 간단합니다. 3.3 이후의 모든 향후 OpenGL 버전은 OpenGL의 핵심 메커니즘을 바꾸지 않으면서 유용한 추가 기능을 추가할 뿐입니다. 새 버전들은 동일한 작업을 달성하기 위한 약간 더 효율적이거나 유용한 방식을 도입할 뿐입니다. 결과적으로 모든 개념과 기술은 현대 OpenGL 버전 전체에서 동일하게 유지되므로 OpenGL 3.3을 배우는 것은 완벽히 유효합니다. 준비가 되거나 경험이 더 쌓이면 최신 OpenGL 버전의 특정 기능을 쉽게 사용할 수 있습니다.

가장 최신 버전의 OpenGL 기능을 사용할 경우, 가장 최신의 그래픽 카드에서만 애플리케이션을 실행할 수 있습니다. 이것이 대부분의 개발자가 일반적으로 더 낮은 버전의 OpenGL을 타겟팅하고 선택적으로 더 높은 버전의 기능을 활성화하는 이유입니다.

일부 장에서는 더 현대적인 기능들이 등장하며, 이는 해당 부분에 별도로 명시되어 있습니다.

## 확장 (Extensions)

OpenGL의 훌륭한 특징 중 하나는 **확장(Extensions)** 지원입니다. 그래픽 회사에서 렌더링을 위한 새로운 기술이나 대규모 최적화 기법을 고안해 내면, 이는 주로 드라이버에 구현된 확장의 형태로 제공됩니다. 애플리케이션이 실행되는 하드웨어가 해당 확장을 지원하는 경우, 개발자는 확장이 제공하는 기능을 사용하여 더 발전되고 효율적인 그래픽을 구현할 수 있습니다. 이를 통해 그래픽 개발자는 다음 OpenGL 버전에 해당 기능이 포함되기를 기다릴 필요 없이, 그래픽 카드가 확장을 지원하는지 확인하는 것만으로 새로운 렌더링 기술을 즉시 사용할 수 있습니다. 확장이 인기를 끌거나 매우 유용한 경우, 결국 향후 OpenGL 버전의 정식 일부가 되는 경우가 많습니다.

개발자는 이러한 확장을 사용하기 전에 사용할 수 있는지 여부를 질의해야 합니다(또는 OpenGL 확장 라이브러리 사용):

```cpp
if (GL_ARB_extension_name)
{ 
    // 하드웨어에서 지원하는 멋지고 현대적인 새로운 기능 수행
} 
else 
{ 
    // 확장이 지원되지 않음: 기존 방식으로 수행
}

```

OpenGL 버전 3.3에서는 대부분의 기술에 확장이 거의 필요하지 않지만, 필요한 경우 적절한 안내가 제공됩니다.

## 상태 머신 (State machine)

OpenGL 그 자체는 커다란 상태 머신(State machine)입니다. 즉, OpenGL이 현재 어떻게 작동해야 하는지를 정의하는 변수들의 집합입니다. OpenGL의 상태는 흔히 OpenGL 컨텍스트(Context)라고 불립니다. OpenGL을 사용할 때, 우리는 주로 옵션을 설정하거나 버퍼를 조작한 다음, 현재 컨텍스트를 사용하여 렌더링함으로써 상태를 변경합니다.

예를 들어 OpenGL에 삼각형 대신 선을 그리고 싶다고 전달할 때, OpenGL이 그리는 방식을 설정하는 컨텍스트 변수를 변경하여 OpenGL의 상태를 바꿉니다. OpenGL에 선을 그려야 한다고 알림으로써 컨텍스트를 변경하는 순간, 이후의 그리기 명령들은 삼각형 대신 선을 그리게 됩니다.

OpenGL 작업을 할 때 컨텍스트를 변경하는 여러 상태 변경 함수(State-changing functions)와 현재 OpenGL 상태를 기반으로 연산을 수행하는 여러 상태 사용 함수(State-using functions)를 접하게 될 것입니다. OpenGL이 기본적으로 하나의 거대한 상태 머신이라는 점을 염두에 두면 대부분의 기능이 훨씬 잘 이해될 것입니다.

## 객체 (Objects)

OpenGL 라이브러리는 C 언어로 작성되었으며 다른 언어로의 많은 파생을 허용하지만, 그 핵심은 C 라이브러리로 남아 있습니다. C의 많은 언어 구조가 다른 고성능 고수준 언어로 잘 번역되지 않기 때문에, OpenGL은 몇 가지 추상화를 염두에 두고 개발되었습니다. 그중 하나가 바로 OpenGL의 객체(Objects)입니다.

OpenGL에서의 객체는 OpenGL 상태의 일부분을 나타내는 옵션들의 집합입니다. 예를 들어, 그리기 창의 설정을 나타내는 객체가 있을 수 있습니다. 우리는 이 객체의 크기, 지원하는 색상 수 등을 설정할 수 있습니다. 객체는 C 언어의 구조체와 유사하게 시각화할 수 있습니다:

```cpp
struct object_name {
    float option1;
    int option2;
    char name[128];
};

```

객체를 사용하고자 할 때의 일반적인 워크플로는 다음과 같습니다(OpenGL의 컨텍스트를 거대한 구조체로 시각화함):

```cpp
// OpenGL의 상태 (Context)
struct OpenGL_Context {
    ...
    object_name* object_Window_Target;
    ...    
};

// 객체 생성
unsigned int objectId = 0;
glGenObject(1, &objectId);

// 객체를 컨텍스트에 바인딩/할당
glBindObject(GL_WINDOW_TARGET, objectId);

// 현재 GL_WINDOW_TARGET에 바인딩된 객체의 옵션 설정
glSetObjectOption(GL_WINDOW_TARGET, GL_OPTION_WINDOW_WIDTH, 800);
glSetObjectOption(GL_WINDOW_TARGET, GL_OPTION_WINDOW_HEIGHT, 600);

// 컨텍스트 타겟을 다시 기본값으로 되돌림
glBindObject(GL_WINDOW_TARGET, 0);

```

이 짧은 코드 조각은 OpenGL을 다룰 때 자주 보게 될 워크플로입니다. 먼저 객체를 생성하고 이에 대한 참조를 ID로 저장합니다(실제 객체 데이터는 비하인드에서 저장됨). 그다음 객체(ID 사용)를 컨텍스트의 타겟 위치에 바인딩합니다(예시의 창 객체 타겟 위치는 `GL_WINDOW_TARGET`으로 정의됨). 다음으로 창 옵션을 설정하고, 마지막으로 창 타겟의 현재 객체 ID를 `0`으로 설정하여 객체 바인딩을 해제합니다. 우리가 설정한 옵션은 `objectId`가 참조하는 객체에 저장되며, 객체를 `GL_WINDOW_TARGET`에 다시 바인딩하는 즉시 복원됩니다.

지금까지 제공된 코드 예제는 OpenGL이 작동하는 방식에 대한 근사치일 뿐이며, 본 튜토리얼 전반에 걸쳐 충분한 실제 예제를 접하게 될 것입니다.

이러한 객체를 사용하는 것의 큰 장점은 애플리케이션에서 하나 이상의 객체를 정의하고, 해당 옵션을 설정한 다음, OpenGL 상태를 사용하는 연산을 시작할 때마다 선호하는 설정이 담긴 객체를 바인딩할 수 있다는 점입니다. 예를 들어 3D 모델 데이터(집이나 캐릭터)의 컨테이너 객체 역할을 하는 객체들이 있을 수 있으며, 이들 중 하나를 그리고 싶을 때 그리려는 모델 데이터가 포함된 객체를 바인딩하기만 하면 됩니다(이 객체들은 사전에 생성되고 옵션이 설정되어 있음). 여러 객체를 보유하면 많은 모델을 지정할 수 있으며, 특정 모델을 그리고 싶을 때 모든 옵션을 다시 설정할 필요 없이 그리기 전에 해당 객체를 바인딩하기만 하면 됩니다.

## 이제 시작해 봅시다 (Let's get started)

이제 명세이자 라이브러리로서의 OpenGL, OpenGL이 내부적으로 대략 어떻게 작동하는지, 그리고 OpenGL이 사용하는 몇 가지 고유한 트릭에 대해 알아보았습니다. 모든 것을 다 이해하지 못했더라도 걱정하지 마세요. 튜토리얼을 진행하면서 각 단계를 거치며 OpenGL을 확실히 파악할 수 있는 충분한 예제를 보게 될 것입니다.

```
